# UI/UX v1 — engineering decisions

Differences between the handoff plan and this repository, and what was done about each. Newest at the bottom. Each entry names the spec it touches and the test that holds it. None of these cancels a core requirement; where a requirement could not be met the entry says so.

## U-001 · Commands run under the arm64 Node toolchain

The non-interactive `node` on this Mac is an x64 build under Rosetta; `node_modules` holds arm64 bindings. Every command in this work is run with `export PATH="$HOME/.local/node-arm64/bin:$PATH"` (arm64 Node 22.23.2, pnpm 12.3.4 via corepack), the same toolchain the production LaunchAgent and `apps/ios/probes/run-probes.sh` use. No dependency was installed or upgraded.

## U-002 · Pinned core tests are not edited; new truth lives in a new layer

Spec: docs/03 §1–2, docs/05. `packages/core/**/*.test.ts` may not be edited (Phase 1 rule in the core vitest config). Several of those tests pin behaviour the new design treats as misleading: a future timestamp clamps to age 0 (`freshness.test.ts`), a null currency formats as USD (`format.test.ts`), `seats_left` 0 means unknown, and the Ask tool notes say fees without a currency are USD (`tools.test.ts`).

Decision: the old functions keep their pinned behaviour for the consumers that still use them (web grid, CLI, Ask tools). The UI/UX v1 surfaces read values only through the new `packages/core/src/lib/workspace/` helpers (`knownSeats`, `knownFees`, `toTimeEvidence`, …), which have their own new tests. Where an old consumer is migrated (the web in M4), it switches to the new helpers rather than the old ones changing meaning underneath it. The Ask tool notes are handled in T15/T16 with the same rule.

## U-003 · The main checkout's `.next` is production; web builds happen elsewhere

`~/Library/LaunchAgents/com.awardgrid.app.plist` runs `next start` on 127.0.0.1:3000 from this checkout, so `.next` is the live site (`DECISIONS.md` rule #67). During T01 preflight on 2026-09-23 this work ran `pnpm build` in the main checkout as a baseline gate, before that rule had been read. That rewrote `.next`; the running server (PID 959, started 2026-09-19) now links stylesheets that 404 (`/login` → `30jnsnx-7tr59.css` 404, `/` stylesheet 500). **This was caused by this work.** Restarting the LaunchAgent would serve a fresh build of `main` 9c69c6c; that is a deploy and is left to the owner. Nothing was killed or restarted.

From here on: no `next build`, `pnpm build`, `check-no-secrets-in-bundle.sh --build` or build-triggering `pnpm e2e` runs in the main checkout. Web builds and web e2e for M4 run in a separate git worktree with its own `.next`.

## U-004 · Quiet Precision tokens are added beside the pinned ones

Spec: reference tokens JSON, docs/02 D11, plan T04. `packages/tokens/tokens.css` is pinned value-by-value by `src/styles/tokens.test.ts` (exact hex, exact key set, achromatic neutrals) and by 24 blocking Linux visual baselines that can only be regenerated by CI. The repo's own token rule is "add tokens, change no values, rename nothing".

Decision: the Quiet Precision palette, type, spacing, radius, motion and z-index values go into a new `packages/tokens/precision.css` export as `--ag-*` properties (light `:root`, `[data-theme="dark"]`, and the system-dark media block, like tokens.css). The iOS shell adopts them in M1–M3. The old `--bg/--fg/--accent…` stay untouched until the web adopts the new system in M4, at which point the web's aliases and the pinned token test are updated together as a deliberate design change with its own evidence, not as a weakening.

`docs/UI.md` rules that Quiet Precision deliberately replaces (accent never a fill, strictly achromatic neutrals, no type above 20px, no icons) apply to the old web surface until M4; the new surfaces follow the approved v1 spec.

## U-005 · The fixture host is a test-only Vite root inside `apps/ios`

Spec: plan T01, docs/02 D10. The plan's `scripts/uiux-fixture-host.ts` is mapped to `apps/ios/fixture-host/` plus `apps/ios/vite.fixture.config.ts`. It mounts the real `App` through `bootstrap()` with explicitly injected fake ports (memory key stores, memory/local file store, a synthetic seats.aero transport and a refusing Anthropic transport). Production `src/main.tsx` never imports it; the iOS build fails if the bundle contains fixture markers. Native HTTP assertions in `src/native/http.ts` are untouched — the host replaces the transport through the existing `BootstrapOptions.fetchImpl` seam rather than faking the native platform.

## U-006 · Fixture scenarios are refused until their state is really seeded

Spec: docs/02 D10, plan T01. The first harness booted every scenario id as the base environment (keys + rows), so `quota-low`, `partial` and `storage-failure` reported "ready" without their defining state — a quiet fallback that would let later "absence" assertions pass without testing anything (found by the T01 review). Now `apps/ios/fixture-host/scenarios.ts` keeps an explicit `SEEDED_SCENARIOS` set; any other id in scenarios.json is refused with the task that will seed it. The set grows as tasks land. Test: `fixture-harness.spec.ts` "the host refuses a missing, unknown or unseeded scenario…" and "each seeded scenario applies its defining state".

## U-007 · The host records a requested language but does not apply it yet

The iOS shell has no i18n until T07/T11. Setting `<html lang="zh-CN">` over English text would mislabel it for VoiceOver and axe, so `openScenario(..., { lang })` is recorded on `#fixture-status[data-lang]` only. When the shell gains a locale, the host passes it to the app and this entry is superseded.

## U-008 · `BootstrapOptions.assertNative` exists so the Anthropic path is testable

In a browser, Ask's native-HTTP assertion refuses before any transport is called, which made every `anthropic: 0` in a browser test vacuous (T01 review, test-validity). `BootstrapOptions` now accepts an optional `assertNative`, passed straight to `createAskService`; production leaves it unset, so Ask keeps `assertNativeHttpAvailable`. Only the fixture host, which injects both transports itself, passes a no-op. A positive-control test proves the counter moves when the app really calls Anthropic.

The production LaunchAgent's working directory is the main checkout, and at startup the server also reads files from it: `openDb()` applies `drizzle/` migrations, `/legal` renders `LEGAL.md`, Ask reads `build/plugin`. ## U-010 · Time provenance: recorded at decode, `unknown` when not recorded, rollback-safe on the web

Spec: docs/03 §1, A03. Decoding now records `time_basis` (which field `computed_last_seen` came from) and `provider_updated_at` (the provider's UpdatedAt as sent), additively; `computed_last_seen` keeps its old meaning for every existing consumer. The new surfaces read times only through `rowTimeEvidence`: a bad or future ComputedLastSeen falls back to the provider's UpdatedAt; a decoded row whose provider sent no time is `local_fallback`; a row with no recorded provenance (older caches, or a store that drops it) is `unknown`, with the fetch time shown separately. On the web, migration `0003_availability_time_basis.sql` adds one nullable `time_evidence` column holding `{basis, updated, at}`; it is read back only while `at` equals the row's `fetched_at`, so a build that does not know the column cannot leave a stale label on values it rewrote. Rollback: previous code runs unchanged against the migrated database (additive column, explicit column lists); no down-migration is needed. Tests: `packages/core/src/lib/workspace/semantics.test.ts`, `src/lib/db/stores/cache-time-basis.test.ts`.

## U-011 · Coverage evidence is recorded where completeness is known and re-checked on every cache hit

Spec: docs/03 §1, plan T03, A05. `runFind` is the only place that knows whether pagination ended, hit the page cap, stopped for quota or was cut short by an inconsistent API page, so it stamps that on the coverage records it writes and returns `FindResult.coverage`. A cache hit re-derives evidence from the records: the newest satisfying complete record counts only if no overlapping record written after it failed to prove completeness (a later fetch replaced some of those rows). Records from before evidence existed prove nothing (unknown). The row replace is atomic where the store allows it (`replaceScope`; SQLite transaction), and an older fetch that finishes after a newer one clears SQLite cell evidence unless it was complete. Web: migration `0004_coverage_evidence.sql` (nullable `cache_coverage.evidence`); previous code runs unchanged against it, and a cell it rewrites with the newer fetch reads back with no evidence. (Correction, pre-merge check: an older-code fetch that started first and lands after a newer one of this build leaves the newer "complete" evidence on its rows. That needs both builds writing at once; see U-058.) `restoreCoverage` exists now and is wired to the workspace snapshot store in T05; the iOS `cache.json` path is protected by the hardened `InMemoryAvailabilityCache.restore`.

## U-012 · The iOS shell's older colour names point at Quiet Precision until their screens are rebuilt; the shell uses the system face

## U-013 · Reduced motion means 0 s, not 0.01 ms

Spec §10: every duration 0 under reduced motion. The shell's global rule used the common `0.01ms` trick, which exists only to keep `transitionend`/`animationend` firing; nothing in the shell listens for them, and a computed `1e-05s` failed the spec check. The rule is now `0s`, and `--ag-motion-*` are `0ms` under `prefers-reduced-motion: reduce`.

## U-014 · Mixed control sizes on not-yet-rebuilt screens are accepted until their task

T04 changes `.ag-button`/`.ag-input` globally (48 pt, Quiet Precision colours). Screens that also set inline sizes or borders (Settings' "Remove key" and "Clear cached results" at the old 44 pt, its first key field with a `--line` border instead of `control-border`, disabled Save buttons with no stated reason) look mixed until they are rebuilt: Search in T06/T07, results in T07–T09, Settings in T11. Each of those tasks' acceptance covers its screen; nothing here is counted as their evidence. Screens: `evidence/screens/t04-app-*.png`.

## U-015 · Type tokens carry a text-scale hook for browser tests

Spec §10 (larger text grows, never clips); plan 01 T04 ("text scaling变量可用于浏览器测试，但不是Dynamic Type验证替代"), plan 04 T21 (`setTextScale(page, scale)`). Every `--ag-type-*`/`--ag-leading-*` is `calc(Npx * var(--ag-text-scale))` with `--ag-text-scale: 1`; nothing in the product sets it. It lets a browser test enlarge all type at once. It is not Dynamic Type evidence — that needs the Simulator or a device and stays unverified until run there. The token guard parses the calc form against the design values; `foundations.spec.ts` doubles the scale and checks that type doubles and a long segment label wraps inside its third.

## U-016 · In the iOS shell a text field never drops below 16 pt

Spec §10 gives desktop inputs 14 px from 768 px, and precision.css follows it (`--ag-type-body` is 14 from 768 px, for the web). The iOS app also runs on iPad (device family 1,2), where a focused field under 16 px makes WebKit zoom in, and Capacitor then blocks pinching back out (T04 review 2). So `.ag-input` in the shell uses `max(var(--ag-type-body), 16px × text scale)`. The web's own fields (M4) follow the desktop spec with a fine pointer. Test: `foundations.spec.ts` "a wide touch screen (an iPad) keeps touch sizes, and fields keep 16 pt text".

## U-017 · The last search is the workspace's shown snapshot

Spec: docs/01 ("last-search.ts … 迁移到版本化工作区适配，不复制数据源"), spec §07 (a relaunch restores the snapshot and shows its time; it does not re-run). Until T05 the last search was a separate in-memory copy set by the Search screen and never saved; a relaunch had none. Now the Search screen's text search runs as a workspace revision (`services.searchText`: parse → `workspace.run` → the engine's shared executor), and `lastSearch` is a view of whatever snapshot the workspace shows: for one produced in this session, the typed text and the engine's answer; for one restored from disk, a view rebuilt from the snapshot alone (`snapshot-view.ts`: its rows, query and coverage; the call count is unknown, null, not the old number) with `savedAt`, which the screen shows as "Saved on this device <age>" by the app clock. The app records each answer before the workspace shows it (the port's `onAnswer`), so a search from this session is never presented as a saved one; only a snapshot the workspace restored from disk is labelled saved. Because that restored snapshot is on screen, Ask may offer it as context. The one existing test that pinned "memory only, a relaunch has none" (`bootstrap-ask.test.ts`) was rewritten to this contract; its other half — the key is never written — is kept. The workspace file holds the query including its `raw_text` (docs/02 D04 allows the query; never the key).

## U-018 · Workspace files are two slots with a generation, not a rename

docs/02 D04: a failed write keeps the last good version. Capacitor's `rename` on iOS goes through a native library not vendored here, so whether it replaces an existing file could not be verified. `SlotFileStorage` keeps `<name>.a.json` and `<name>.b.json`, each `{generation, value}`; a write goes to the slot not holding the newest good version; a read takes the good slot with the higher generation. A torn or failed write can only damage the slot being written. Cost: up to twice the workspace's size on disk (the workspace itself is capped at 10 snapshots / 5 MiB). The workspace writes only when something it saves changed since the last save or restore.

## U-019 · The Search screen keeps the shown results through a new search

## U-020 · A queued run that a newer run superseded is not sent

docs/03 §3; T05 review. The workspace aborts a run's signal as soon as a newer run starts; the production search port runs searches one at a time and skips a queued one whose signal is aborted, before any request (its answer could only be dropped). A request already sent cannot be recalled (docs/PHASE0.md §3), so a superseded run that was already under way still completes and may cost calls; the quota counter records them. The run handle's `signal` and `meta` are additive fields on the core `SearchRun` type.

## U-022 · A query built in the editor carries a sentence that describes it

A QueryObject's `raw_text` is shown as the search's text (the Search screen's box, Ask's "last search"). After fields are edited, the words originally typed no longer describe the query, so the editor sets `raw_text = describeQuery(query, dateRule)` ("HKG to SEA, next 30 days, business, nonstop, on Air Canada Aeroplan, under 80000 miles"). It says everything the deterministic parser can read back, and a rolling rule stays "next N days". Whether a text does read back exactly is decided by `textReproducesQuery` (U-024): the mixed-cabin rule and dynamic pricing have no words, and a lone airport that shares its city's code reads back as the city.

## U-023 · Places are named from the seed's aliases; dates use the platform date picker

The places seed (packages/core/data/places.json) has metro → airport lists and zh/en aliases but no airport dataset. An option or chip is named by the airport's own alias where one exists (Narita, 浦东), else by its metro (JFK → New York); a metro is offered with its airports spelled out ("All airports: NRT, HND") and adds all of them. A 3-letter code the seed does not know can be added as typed. Fixed dates use `<input type="date">` (the iOS wheel picker on a device): a value that is not a calendar date cannot be entered there, and core's `resolveDraft` checks the calendar anyway. Relative days are counted in UTC from today, including today, and the editor shows the exact range. The shared primitives gain a `Switch` (button, `role="switch"`, 48 × 28 track in a 44 pt target; on = thumb moved and accent fill).

## U-024 · Run and Watch use the box text only when it reproduces the search on screen

T06 review. Run re-reads the Search box, and a watch stores it as text (watches become structured in T14). For a search whose text cannot reproduce it — `textReproducesQuery(text, query, day it was made)` is false — reading the text again would silently run a different search. So when the box is unedited and does not reproduce the shown search, Run runs that search's structured query (`rerunShown`), and "Watch this search" is disabled with the reason stated. Reading "as of the day it was made" keeps typed rolling text ("next 30 days") faithful: re-running it later rolls, as the words say.

## U-031 · Calendar numbers are compact K in both languages, rounded up and marked; narrow or large text gets a date list

T08, spec §14. A day cell at 390 is ≈ 47.7 pt, 46 pt inside. Measured in the fixture host: "≈6.85万" needs 57 pt and "≈110.5K" 62, so neither the 万 form at useful precision nor an inline "≈" fits. The cell shows thousands with at most one decimal below 100K and none above ("68.5K", "111K"; "1.3M" past a million) in both languages — the K form Chinese mileage users also write — rounded UP, so a cell never shows a price lower than the real one; a rounded value carries a small "≈" in the cell's corner, explained in the legend, and the cell's accessible name and the day's options carry the exact miles. Where a column would be narrower than 44 × `--ag-text-scale` (320 wide, or larger text; measured on the content box, without the gutters), the calendar becomes a list of the days with options, full numbers, each opening its options right under its row, plus a line per kind of other day. Weeks start on Sunday in English and Monday in Chinese. An empty day says which kind of empty it is, by mark and in words (spec §14: none, not checked, not covered): "–" no matches (checked to the end), "…" not checked to the end, "?" coverage unknown, "⊘" not monitored, "∗" hidden by the view filter; the legend names each mark shown.

- It returns null only for "no such file". On iOS the plugin rejects that with `OS-PLUG-FILE-0008` (its `FilesystemError.fileNotFound`, read from `@capacitor/filesystem` 8's Swift source; not yet seen on a device). The web version says "does not exist".
- Any other error is thrown.
- The best-effort readers keep their meaning: an unreadable cache, quota or watches file is still a cold start (`SnapshotStore`). Ask's store already caught.

**The two-slot storage** (`SlotFileStorage`)
- A slot whose read fails could hold the newest version. While one cannot be read, `read` throws and `writeAtomically` refuses.
- A slot that reads but does not parse is a torn write, the case the format exists for: the other slot is used.
- Both slots present and neither readable is unreadable, not empty.

**Tests.** The T05 test "junk in both reads as nothing" now expects "unreadable" (an iOS test, updated with this reason). New tests cover a slot that cannot be read and two torn slots, and the favourites store over the real storage.

**Effect elsewhere.**

## U-048 · A watch is its structured query and date rule; old text watches are migrated only on the parser's proof

T14, plan 03 T14, docs/02 D05, docs/03 SavedQueryV2, docs/04 S07.

**What a watch is now**
- `Watch` (core `watch/watch.ts`) may carry `draft` (the structured query and its date rule), `review` ("dates" or "unparsed") and `unseenChanges` (what changed, with old and new miles, newest first, at most 30).
- `lastResult` also records:
  - `compared`: the dates both checks covered. It is null when the check could not compare, and absent on results from before T14, where it is unknown, so neither sentence is shown.
  - `refused`: a 401 or 403.
  - `unresolved`: the conditions could not be run.
- `SavedQueryV2.draft` is `QueryDraft | null`, with an optional `review`. This widens docs/03's type: a text the parser cannot read keeps no draft instead of a guessed one.
- `watches.json` is version 2. Version 1 is still read.

**Migration** (core `workspace/watch-migration.ts`)
- It runs at launch, after the store is read, using the deterministic parser only (no AI and no request). The v1 file is copied to `watches.v1.json` once, before the first write.
- The date rule is proven by reading the phrase on four days: today, tomorrow, the day after its first date, and the day after its last.
  - **Relative** when today's and tomorrow's windows start on each day with the same length ("next 30 days", "未来两周").
  - **Fixed** only when all four readings give the same dates, which in practice means full ISO dates. A month name read in September gives Oct 1–31 twice, but the rest of the month once October starts. A date without a year moves to next year once it has passed. Both are **unclear** (review finding MIG-02).
- An unclear watch keeps its text and is still checked by it, as before, marked `review: "dates"`.
- A text the parser cannot read keeps no draft (`review: "unparsed"`) and is still checked by its text. None is dropped.

**A new watch** of the search on screen (`draftForWatch`)
- It keeps the snapshot's own query, so every structured field goes through: programs, nonstop, mixed cabin, mileage cap and dynamic pricing.
- Its dates are relative only when its sentence proves it and gives exactly those dates. Otherwise they are fixed: a search for "October" watches Oct 1–31 and does not roll to next year.
- The "this search cannot be watched by its words" gate (`watchNeedsText`, T06) is gone: any search can be watched.

**The runner** (`apps/ios/src/watch/runner.ts`)
- **What it runs.** A structured watch runs `resolveDraft(draft, today)` through `engine.searchQuery`, never its old text read again. A watch under review, or one not migrated, reads its text.
- **What it does not run.**
  - Fixed dates that have all passed are skipped as `dates_passed`, and nothing is spent.
  - A draft that no longer resolves (a damaged file) is not replaced by the text. Nothing is sent, and the card says the conditions need editing (review finding RUN-03).
- **Unchanged from before:** sequential checks, quota re-read between watches, the 45-minute attempt clock, the first check setting a baseline only, a quiet check keeping unseen changes, and a failure leaving the baseline. A refused key also starts the attempt clock.
- **An edit made while a check is out wins** (review finding RUN-01). Each watch is read when its turn comes, and again when its request returns. If it was edited, restarted or removed meanwhile, that check writes nothing. Unseen changes are carried from the watch as it is now, so what was marked seen stays seen.

**Editing a watch**
- The query editor has a watch mode: the title "Edit watch", no text search, and "Save watch" with "Saving sends nothing."
- Saving stores the conditions and date rule, clears `review`, and restarts the watch: the baseline is cleared and the next check sets a new one, reporting nothing.
- Leaving with unsaved edits asks in the watch's own words.

**The Watches screen (S07)**
- **Card heading and conditions.** Each card is headed by its route, in the screen's language. Its conditions line starts with "Next N days" for a moving window and names the programs, not a count.
- **Control names.** Edit, the switch and Stop are each named with the full heading and conditions. The Stop sheet shows the conditions too.
- **The state line.** Each state is said only while it is true:
  - A failure newer than the last success is said even when it held this run's check back. It is never "cached results are still valid" (review findings RUN-02 and UX-02).
  - "Dates have passed" is not said once the dates are edited (UX-03).
  - "Previous baseline kept" is said only when there was one (UX-04).
- **Unseen changes** are listed in `<details>` and marked seen when the screen opens.
- **"Watch saved"** is set just after the page appears, into a status region that is already present and empty, so it is announced. The history entry then forgets it.

**Duplicates.** Two watches are the same when their conditions and date rule are, whatever the sort (U-030). Editing one watch into a copy of another is allowed (review finding MIG-06 was refuted: the spec does not ask for it).

**Fixture.** `watch-baseline`, `watch-changes` and `watch-failure` are seeded. The harness's "unseeded" example is now `ai-pending` (T16).

## U-056 · Cross-size and accessibility, measured screen by screen; the fixes are layout, not the reference

T21, plan 04 T21, A35, A36.

**What is measured** (`e2e/uiux/layout-audit.ts`, used by `responsive.spec.ts` and `visual.spec.ts`). For each screen, width and text scale, the audit reports:
- the page being wider than the screen;
- text cut by its own box (overflow hidden or clip, with no ellipsis intended);
- text spilling out of a box that lets it show;
- words running out of the control or cell they belong to (a button, a radio, a gridcell, a label, a link), even from a child span that grows to fit them: a segment's label hanging out of its button, a row's value wrapping past its row, a day's words running into the next day;
- a box that clips cutting off content, whether its own text, a child's, or a control with no words. A declared ellipsis excuses a cut only where one can be drawn: one unwrapped line of a block box cut sideways, or a line clamp. A flex box, or wrapped lines cut in height, cut the words with nothing to say so;
- a select's or a field's value wider than the field, unless it ends in an ellipsis on purpose (measured with the field's own font);
- text past the screen's side outside a sideways scroller;
- controls that cover each other;
- glyphs drawn over other glyphs: each text's line boxes (`Range.getClientRects`) must not cover another's, or another line of the same text, by more than a quarter of the smaller line's height (a glyph box is taller than its font size, and a CJK font's more so).

The last two are about what is on screen. So the audit first measures with every screen-level scroller at its top, wherever the page was left: the page, an app screen's own scroll area, the matrix's. Then it steps each scroller through its whole height, a little less than its visible part at a time. A scroller inside another is first brought into view. Every scroll position is then put back. On iOS, `documentScrolls` also checks that the shell's document never scrolls.

It is measured against the layout viewport (`clientWidth`). A mobile browser zooms out to fit a page that is too wide, and widens `innerWidth` with it. The plan's own check (`scrollWidth > innerWidth + 1`) therefore misses exactly that overflow. It is kept verbatim, beside the stronger checks.

What counts as seen:
- a box as cut by its scroll areas;
- text under `aria-hidden`, like anything drawn: the attribute hides it from assistive tech only (much of the calendar's and matrix's text is `aria-hidden`, since their cells are named whole);
- no hidden or inert content (`checkVisibility`: a closed `<details>`; 1-px screen-reader text);
- fixed layers (a bar, a sheet) compared only among themselves. Sticky parts count with the page at rest; once scrolled, each is a layer of its own, since content passes under them by design;
- with a modal dialog open, only the dialog's controls and text.

**The audit is checked.** `audit-proof.spec.ts` puts each defect it is for on the page, expects the audit to name it, then takes it away and expects the audit clean again:

## U-058 · Upgrade and rollback, checked against the old code itself

T22, plan 04 T22 Step 3 ("record migration versions and failure recovery; old versions stay readable, keys and quota untouched"); docs/07 safe rollback.

**What is on a device, by version.** The old app wrote the files marked "old". The new build writes the rest, each in its own namespace; nothing new is written into an old file's shape.

| Web browser storage | new | keys per account (T18) | ignored by the old build |

**How it was checked** (evidence T22):
- **Upgrade.** The fixture `apps/ios/src/app/__fixtures__/pre-uiux-device.json` holds the files the app at `9c69c6c` wrote after ordinary use: a question that searched, two watches, 600 calls. That commit's own code produced them, in a throwaway worktree. `upgrade-from-pre-uiux.test.ts` starts the new build on them, then uses it (a search, a saved snapshot).
  - Starting the new build (`bootstrap`: restoring and migrating) reads everything, sends nothing and never reads, writes or clears a key.
  - The cache, quota and conversation files are left byte for byte.
  - Opening the app then checks due watches with the stored key, as the old build did (`App.tsx`). That reads the key, spends calls, and saves the cache, quota and watches in the shapes above (review MIGR-01; tested).
  - Both watches are kept: one structured, one waiting for review. The v1 file is copied first.
  - Using the build adds `workspace-v1` and `favorites-v1` and deletes nothing. The quota and cache keep the old shape.
- **Rollback.** The old code (`9c69c6c`) was run on what the new build left.
  - It reads the quota (601), the conversation and the cache. Its own save changes and deletes nothing, and it leaves the new namespaces alone.
  - It reads no watches from the version-2 file. It does not write over it either, until a watch is added.
- **The Web.** The current build wrote a row and a coverage record with evidence into a database migrated to `0004`. The old server's store opened it (its own migrations are a no-op there), read the row (70,000) and its coverage, and wrote a newer row. Read back by the current build, that row's time and coverage are unknown, not stale.

**Rollback order** (nothing is deleted, keys and quota are never reset):
1. Stop the new build (no new writes).
2. Keep a copy of the new files with their versions: `watches.json` (v2), `workspace-v1.*`, `favorites-v1.*`, `settings-v1.*`.
3. Put `watches.v1.json` back as `watches.json`. That is the watches as they were at the upgrade; changes made since are in the v2 copy.
4. Install the previous build. The Web: redeploy the previous commit. The database needs no down-migration.

**Known limit:** watches added or edited in the new build do not survive a rollback into the old build's file. They are in the kept v2 copy and come back with a roll forward.

## U-059 · The Simulator pass: the chosen appearance reaches the native side (U-042 closed), and Dynamic Type drives the text scale

T22, with U-042 (T11) and A35's native half (T21). Checked on the iOS Simulator (evidence T22). The Simulators were fresh devices with no keys, so nothing was sent to a paid service.

**U-042, as found.**
- **The status bar is readable** under a theme chosen against the device's own: light text over the dark header, dark over the light one. That holds before any change on iOS 26.5 both ways, and on 18.3 for Dark chosen on a Light device (the only 18.3 case captured). The native gap U-042 feared is not there.
- **The web view's own background was wrong.** Capacitor makes the web view the root controller's view and paints it `systemBackground`, which follows the device. So the strip under the tab bar, around the home indicator, was white under a dark app and black under a light one.
- **The fix, a few lines of native code as U-042 planned:**
  - `ios/App/App/AppViewController.swift`, a `CAPBridgeViewController` subclass, is now the scene's root controller (`SceneDelegate`).
  - It receives `agAppearance` from the page (`apps/ios/src/native/appearance.ts`): the chosen scheme and the page's bottom surface colour, posted whenever the theme applies and whenever the device's appearance changes.
  - It sets the window's interface style, so native parts such as the keyboard follow the choice, and paints the web view's background that colour.
  - No plugin, no dependency. In a browser there is no handler, and nothing is posted.
- **Checked:** Dark on a Light device, Light on a Dark device and System on a Dark device (iOS 26.5), and Dark on a Light device (iOS 18.3). The strip now matches the tab bar pixel for pixel. System on a Light device, and Light on a Dark device on 18.3, were not captured (corrected after the T22 honesty audit).

**Dynamic Type, as found.** Nothing on the device set `--ag-text-scale`, so the app ignored the system's text size entirely. At the largest accessibility size the text was unchanged (Simulator). The browser tests could not see this: they set the scale themselves.

**The fix** (`apps/ios/src/native/text-size.ts`):
- WebKit on iOS resolves `-apple-system-body` to the body size the person chose (17 at the default). Its ratio to 17 is the scale, held between 1 and 2, the range T21 verified. A person who chooses smaller text keeps 100%, and the largest sizes stop at 200%.
- A hidden probe in that font is watched, and read again when the app returns to the front.
- It runs only in the app on iOS. Elsewhere the font is unknown and a test's own scale stands.
- **Checked on the Simulator:** Large (100%), xxxLarge (≈135%), AX Large (≈194%) and AX xxxLarge (200%, the cap) on the first screen.

**Not checked on the Simulator:** screens past the first. Their layout at 100–200% was verified in Chromium (T21); a real WebKit pass over them, VoiceOver and a device remain.

**The owner's test Simulator** (the device `run-probes.sh` uses) already held app data and a seats.aero key. The T22 build was launched on it once, before this was seen.
- Nothing was tapped and nothing was sent (its `quota.json` is unchanged).
- On leaving, the app re-saved `cache.json` and `ask.json` in their version-1 formats, which the old build reads (U-058).
- The previous build (the main checkout's Simulator build of 23 September) was installed back, and every later Simulator step used fresh devices.
